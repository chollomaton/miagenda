## Arquitectura congelada

Autoridad Apple/Mac → publisher → Firebase mirror → reader/cache web.
Ningún contrato de lectura contiene save/push/commands. Online 1.1 separado.
Namespace Firestore válido: users/{owner}/icloudMirror/state (documento),
subcollections objects/{hash}, buckets/{hash}, generations/{generationId} bajo ese
documento. Los segmentos alternan colección/documento: no usar un path impar.
Los payloads son objetos y buckets inmutables direccionados por SHA-256;
manifest liga hashes, counts, source/schema/version/timestamps/calendarScope.
State currentGeneration + previousGeneration cambia sólo tras validar/publicar
completamente. rootHash cubre contenido y contexto de source (sin publishedAt ni
ID de generación, para detectar no-op global); cada bucket liga ID/tipo/hash.
No TTL. GC futuro conserva ambas generaciones y toda referencia, con grace period
para readers/publishers concurrentes; sin GC destructivo en este bloque.
Cache aislada por owner+publisher, validación antes de transacción de activación,
retención actual/anterior. Descargas incompletas/corruptas no cambian actual.
Boot offline revalida cache. No credenciales ni transporte productivo activado.
Feature local de preview nunca cambia default Online. Datos demo etiquetados,
ninguna mezcla de entidades ni sesiones. Reader no hereda SyncEngine/AgendaStore.

## Publisher: scaffolding local, integración pendiente

CloudSourceMonitor observará EventKit y iCloud Drive; gate starting/importing/
settling/ready/error, quiet period, fingerprint global y snapshot acotado coherente.
Un actor MirrorCoordinator serializa publicación, comprueba gate/revocation antes
cada fase y CAS de puntero; no publica durante refresh incompleto ni error.
SnapshotProvider es sólo lectura de stores ya cargados; no llama boot/migration/import.
Canonicalizer/Hasher/Validator deben compartir fixtures golden UTF-8 con TS antes
conectar MirrorTransport. Monitor detecta cambios; snapshot define publicación.
Sin señal fiable de completitud de EventKit se necesita confirmación de scopes y
settling documentado; nunca presentar ready como certeza de todo iCloud.

## Pairing y seguridad pendiente de backend

Identidad publisher separada (anonymous UID persistente en Keychain nuevo), owner
Google. Challenge aleatorio 256 bits, sólo hash persistido, TTL lógico cinco minutos,
un solo uso, owner confirma en navegador y transacción liga UID activo/lease.
No tokens en URL/logs, callback allowlist, lease/revocación comprobados antes publicar.
No exportar Keychain/Vault; no conceder acceso users/{uid}/entities al publisher.
Matriz: owner lee mirror y gestiona publisher; no escribe mirror. Publisher activo
escribe sólo mirror del owner; no entidades 1.1. Terceros nada. Cambio de publisher
invalida cache/descargas en vuelo. rootHash verifica integridad, no autenticidad;
requiere autorización de rules. Coste cero en pruebas locales, no promesa de coste
cero de Firebase real. No Firebase emulator/rules harness encontrado: plantilla
local futura deberá validarse en emulador antes cualquier despliegue.

## Implementación efectiva y límites del bloque

Wire TS: source discriminant `apple-agenda`, fuente real descrita arriba. No se
copian relojes de 1.1 ni se fuerzan UUID. Envelopes estrictos y proyección de
metadata resuelta por provider; flags hasOverride y sourceCopyKey no se exportan.
DateComponents wire es {date,time,timeZone}, null timezone = floating. Fecha evento
UTC conserva instante; UI usa Europe/Madrid. La fuente portable no incluye timezone
del evento/all-day: completar esto con provider antes certificación de calendarios
fuera de Madrid. Las series preservan reglas completas pero UI no expande ocurrencias.
Fixtures de tree/trash se adaptan a labels planas/tombstones reales, con explicación.

Contrato/canonical/generation/validation, transport de lectura Memory, reader sin
commands, caché IndexedDB por owner+publisher con current/previous y CAS revision.
Boot revalida y puede volver a previous. Epoch y callback de autorización esconden
datos tras invalidación; identidad concreta nueva requiere reader/cache nuevos.
Todo refresh descarga/valida snapshot entero antes activar; no optimización de reads
remotos ni seguimiento automático Firestore implementado. Esa optimización debe
retener exactamente las mismas comprobaciones de integridad y sesión.

UI MirrorApp usa AgendaDataSource; Online sigue App/AgendaStore sin branches mirror.
Preview sólo DEV + ?mirrorPreview=1, Online default; build final elimina demo.
Apariencia en espejo es local de la vista, sin Preferences writable en mirror.
Pairing TS ofrece interfaces, challenge local 256-bit/5 min y especificación de
policy probada; ninguna función crea un grant real. No emulator/rules harness en
repo: no se crea falsa garantía de rules, ni se altera firestore.rules productivo.
No adapter Firestore real: límite deliberado de interfaz permitido por fase D.

Native package usa golden snapshots iguales a TS, actor gate y stage/CAS mock.
Canonicalizer nativo falla con números no enteros hasta certificar formato Double
ECMAScript; validator nativo cubre envelope y relaciones básicas, no nested payloads
completos. El paquete no está enlazado a Xcode ni puede publicar datos reales.
GC queda diseñado, sin ejecución; no TTL. Pairing Firebase/Keychain queda pendiente.

Vista local: Vite nonce por respuesta para scripts/styles inyectados y HMR sólo
loopback; index.html y CSP del build final intactos. API contrastada con documentación
oficial https://vite.dev/guide/features.html y config/shared-options.
Vitest limitado a 4 workers tras reproducir timeouts bajo saturación; prueba focal
original m5-performance y preview pasó antes del cambio de workers.
