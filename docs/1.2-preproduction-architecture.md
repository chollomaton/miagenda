# Mi Agenda 1.2 — arquitectura de preproducción, 9 octubre 2026

## Frontera y modo de ejecución

El lector web sigue siendo exclusivamente `iCloud · Solo lectura`. Firebase Auth identifica al owner por Google; un UID **anónimo distinto** identifica al publisher. El publisher no recibe credenciales Google, no escribe `/users/{owner}/entities` y no modifica EventKit ni JSON. No hay Functions, Admin SDK, servidor de autoridad ni Blaze en la nueva ruta. Spark debe mantenerse sin facturación asociada; al agotar su cuota se acepta indisponibilidad y se conserva la copia validada, nunca se migra automáticamente de plan.

El servidor `emulator/authority.ts` sigue existiendo como harness histórico y no es desplegable. La ruta nueva usa Firebase Auth REST oficial en Swift, Firestore REST autenticado con ID token en Swift y SDK Firebase Auth/Firestore Lite en la web. Se optó por REST oficial para el publisher sin añadir dependencias remotas al paquete Swift existente; no se pide ningún token manual. Esto es una diferencia explícita frente a integrar FirebaseAuth para Apple. No se afirma estar usando ese SDK ni su persistencia Keychain.

Referencias oficiales: [Auth REST](https://firebase.google.com/docs/reference/rest/auth), [Auth anónimo Apple](https://firebase.google.com/docs/auth/ios/anonymous-auth), [transacciones](https://firebase.google.com/docs/firestore/manage-data/transactions), [condiciones y getAfter](https://firebase.google.com/docs/firestore/security/rules-conditions), [Spark](https://firebase.google.com/pricing).

## Identidad y custodia nativa

`PublisherIdentity` crea la identidad sólo al conectar explícitamente. Restaura el UID/refresh token del Keychain, refresca automáticamente el ID token y rota el refresh token antes de activar la sesión. El ID token vive sólo en memoria. Error de persistencia, refresh denegado, cambio de UID inesperado o configuración ambigua fallan cerrado. La pérdida del item no crea silenciosamente otra identidad al pedir un token; conectar de nuevo es una acción explícita. Un item corrupto se elimina y se informa del fallo antes de permitir un nuevo intento.

`KeychainPublisherCredentialStore` usa generic password, servicio por entorno/proyecto, `kSecAttrSynchronizable=false`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. No usa UserDefaults, archivos, JSON externos, iCloud o logs para credenciales. La codificación JSON es interna al valor binario del item Keychain. Otro servicio `.binding` guarda ownerUID y publisherID para restaurar la vinculación. No duplica persistencia de un SDK: el SDK Apple no forma parte de esta composición.

Cerrar sesión incrementa un epoch que impide que una respuesta pendiente reactive la sesión. El transporte HTTP es efímero, no conserva cookies/cache y rechaza redirects. No registra cuerpos ni tokens. Revocar y cerrar sesión primero revoca el grant con CAS y después borra los items; si no hay red, la UI informa del fallo y no finge revocación remota. El owner puede revocar/reemplazar desde Ajustes. Hay además cierre local explícito para un Mac offline o reemplazado: borra credenciales/binding sin fingir revocación remota. Borrar el Keychain local no equivale a revocar un ID token emitido: el grant/lease es la autoridad de escritura. Reinstalar en el mismo Mac puede conservar items; restaurarlos no evita revalidar el grant. Un lease caducado requiere pairing nuevo.

## Pairing, autoridad y publicación

1. El Mac genera 32 bytes con SecRandomCopyBytes. El ID del documento es SHA-256 de la representación JSON canónica del secreto hexadecimal, igual en Swift/TypeScript.
2. Crea `/mirrorPairing/{challengeID}` con su UID anónimo, fecha de creación del servidor y caducidad menor de cinco minutos. No se puede listar esa colección. El challenge es una capacidad: conocer su hash permite consultar una solicitud aún vigente estando autenticado. No se debe compartir enlace ni código.
3. El enlace lleva el secreto en el fragmento `#pair=...`, fuera del request HTTP y Referer. La web lo captura en memoria y borra el fragmento de su historial inmediato. También recibe un nuevo enlace en una pestaña ya abierta. No hay analytics. Extensiones/historial externo/clipboard no quedan bajo control de la aplicación.
4. En Ajustes → Fuente y sincronización, el owner Google revisa y confirma explícitamente. Una transacción consume el challenge y sustituye el único grant del owner. `getAfter` obliga a que ambas escrituras estén ligadas; replay, expiración y consumo separado se deniegan.
5. El Mac confirma explícitamente después de la aprobación web y revalida owner/publisher/challenge/lease. La selección de carpeta y calendarios Apple y el inicio de publicación son acciones separadas.
6. Stage crea objetos/buckets/manifiestos inmutables, reutilizando contenido idéntico ya presente. Activate usa precondición `updateTime`/`exists=false` y conserva previousGeneration. Las reglas comprueban el grant vigente en ese commit. Una marca `/users/{owner}/mirrorActivations/{generation}` se crea en el mismo commit: cada generación sólo se activa una vez, evitando replay/ABA a una generación anterior.
7. Renovación acotada a una hora, únicamente antes de caducar y sin cambiar identidad. Revocación sólo por owner o publisher actualmente asociado; un publisher caducado puede revocarse pero no renovar ni publicar. Reemplazo impide inmediatamente stages/activaciones del anterior, incluso con un ID token aún válido.

Firestore Rules no calculan SHA-256 ni recorren arbitrariamente una generación grande. La validación de contenido completa sigue en el builder Swift y en el reader web; las reglas garantizan **autoridad, inmutabilidad, binding del manifiesto y activación**, no que un publisher autorizado comprometido publique contenido verdadero. La web rechaza contenido inválido y conserva la última copia validada. No se equipara esta frontera a la validación privilegiada del harness anterior. No hay GC remoto automático en la ruta nueva: quedan objetos y challenges históricos sin permiso de listado/borrado por clientes. La retención debe vigilarse dentro de las cuotas Spark.

## Rutas y matriz

| Ruta | Owner | Publisher asociado y lease válido | Terceros |
|---|---|---|---|
| users/{owner}/entities/{id} | leer/crear/actualizar; delete prohibido, política 1.1 exacta | nada | nada |
| mirrorPairing/{hash} | confirmar Google en transacción; get por capacidad vigente o owner confirmado | crear anónimo; get de sus challenges | sin list; get sólo con capacidad vigente y autenticación |
| users/{owner}/mirrorControl/grant | get, confirmar/reemplazar, renovar vigente, revocar | get, renovar vigente, revocar | nada |
| users/{owner}/icloudMirror/state | get | get y CAS con grant/manifiesto/marca nuevos | nada |
| .../state/{objects,buckets,generations}/{id} | get | get/create inmutable | nada |
| users/{owner}/mirrorActivations/{generation} | get | create atómico con state; get | nada |

El owner no escribe mirror data ni sus marcas de activación. No se concede delete al owner en la agenda 1.1. Listados de contenido no son necesarios para el reader ni el publisher.

## Configuración pública y guardas

Web: `VITE_CLOUD_BACKEND=firebase`, `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`. El pairing necesita `VITE_MIRROR_ENABLED=1` y `VITE_MIRROR_ENVIRONMENT=production`. Un build dev exige además `VITE_MIRROR_ALLOW_PRODUCTION_DEV=1` para conectar con Firebase real. Sin este opt-in permanece desconectado. Config solicitada pero ambigua falla antes de crear clientes. Ninguna URL de emulator se admite en la entrada normal.

Mac: el Info.plist señala `MirrorPublisherConfigFile` al nombre sin extensión de un plist público incluido como recurso del target. Su diccionario de strings contiene `MIRROR_ENABLED`, `MIRROR_ENVIRONMENT`, `FIREBASE_PROJECT_ID`, `FIREBASE_API_KEY`, `FIREBASE_APP_ID`, `MIRROR_PAIRING_URL`. La clave pública de API no otorga autoridad: la otorgan Auth y Rules. No se incluye service account, client secret, refresh token ni credenciales owner. Ejemplo desactivado: `MirrorPublisher/PublisherConfig.example.plist`. Para DEBUG real se exige además `MIRROR_ALLOW_PRODUCTION_DEBUG=YES`; Release rechaza preprod. URLs públicas sin usuario/password/query/fragment; producción HTTPS. Endpoints Auth/Firestore no son configurables libremente.

Preprod fija proyecto demo, clave sintética y puertos 19099/18080, sólo DEBUG/loopback. El probe Swift usa las mismas clases de identidad/transporte/config que producción, con store en memoria para credenciales exclusivamente sintéticas. La web usa el lector habitual, el mismo servicio de pairing y SDK Google sintético. El probe no abre EventKit, iCloud ni Keychain. El Keychain se verifica aparte con mocks y un item sintético temporal que se elimina. El build web normal excluye todo el código/config de emulator y las fixtures.

## Boot y operación

Sesión owner restaurada: dashboard directo; copia local validada se adopta antes de esperar la descarga. Sin sesión: gate mínimo Conectar Mi Agenda/Google. La copia se limita por proyecto/UID/publisher y no se muestra a otro usuario. El botón Actualizar se conecta a la sesión aun si no había primera publicación al arrancar. Pairing queda en Ajustes; sólo un enlace explícito abre esa sección. Sin selector Online ni agenda editable en el flujo normal.

En el Mac, sin recurso de configuración no aparece el panel ni se construyen clientes. En DEBUG, señalar `MirrorPublisherConfigFile` abre directamente el panel productivo aislado, sin construir el AgendaStore original; sin ese recurso sigue disponible el harness local anterior. En Release el panel se integra en Ajustes → Cuentas. Su modelo vive durante la sesión de la app, por lo que cambiar de pantalla no detiene el driver. Con configuración activada, el panel permite vincular/restaurar/renovar/revocar y escoger carpeta/calendarios antes de iniciar el driver. Ninguna fuente se publica automáticamente al abrir la app. La cobertura inicial es seis meses antes/después del inicio de esa sesión de publicación; permisos y disponibilidad local se verifican por el provider existente. La selección no se persiste, por lo que tras reiniciar se vuelve a escoger e iniciar explícitamente.

## Rollback futuro

Detener driver, revocar el grant owner cuando haya conectividad, desactivar el gate web/nativo y restaurar las Rules 1.1 exactas del archivo raíz previamente conservado. Esto cierra la superficie mirror remota sin modificar entities 1.1, EventKit ni los JSON iCloud. No borrar datos Apple ni usar scripts de limpieza masiva. Conservar última copia local validada bajo su scope owner; cerrar sesión oculta los datos al siguiente usuario. Las marcas/challenges huérfanos se pueden conservar hasta una limpieza explícita futura autorizada. No hay rollback/deploy ejecutado aquí.

`npm run check`; `bash scripts/run-mirror-emulator.sh tests` para suites históricas; `bash preprod/run.sh <repo-nativo-aislado>` para 3 repeticiones de Rules nuevas y E2E nativo/web. Requieren Java local y dependencias ya instaladas. No ejecutar suites contra el mismo emulator simultáneamente: los tests borran sólo el proyecto demo sintético. Probe y scripts rechazan credenciales administrativas reales. Nativo: `swift test --package-path MirrorPublisher`, `bash scripts/test_app.sh <scratch>`, Xcode Debug/Release con `CODE_SIGNING_ALLOWED=NO` y DerivedData aislado. ## Evidencia visual e incidente del host

Las capturas finales se generaron con una copia DEBUG de ruta e identificador exclusivos, seleccionada por bundleURL exacto y PID, nunca por el nombre de la app instalada. El host representativo recibe solamente la fixture sintética y no activa Auth ni publisher. Light/dark se inyectan sólo a esa copia, sin cambiar la apariencia del sistema. En web se verifican light/dark/system y móvil sin desbordamiento horizontal ni solicitudes externas.

Durante la primera pasada, `ensureEventsLoaded` no respetaba `unitTestHost` y leyó eventos reales al entrar en Calendario. Se eliminó la captura contaminada y se regeneraron todas las capturas nativas. Se añadieron guardas al refresh, lazy load, permisos, acceso a CloudSync y migraciones, con regresión de aislamiento. La ruta antigua podía ejecutar migraciones: la ausencia de clics de edición no basta para afirmar que no había una vía de escritura. Los dos JSON de iCloud mantienen los hashes del informe certificado anterior; una auditoría únicamente de lectura no encuentra eventos modificados en la fecha del Work dentro de la ventana abril 2026–abril 2027. Es evidencia acotada, no una baseline EventKit completa antes/después.

Paridad: sidebar 225 px, ritmos de tarjetas, encabezados, radios, detalle de nota y master/detail de Ajustes ajustados; Calendario mensual incorpora selección y panel del día. Los materiales vibrantes AppKit, SF Symbols, toolbar de ventana y estados de foco son aproximaciones en CSS. La web permanece de consulta: no se replican botones de edición, Bóveda o preferencias que gobiernan el Mac. El TimeBlock de la fixture se representa como EKEvent no guardado en el host nativo para comparar la misma agenda; no se llama a save/commit ni a reconciliación de fuentes reales. No se afirma identidad píxel a píxel ni una comparación exhaustiva de todos los tamaños.
